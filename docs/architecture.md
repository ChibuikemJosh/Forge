# Forge Architecture Foundation (Task A)

## Repository structure

Task A uses a modular monolith with two application parts that run as separate
development processes and communicate over HTTP.

```
forge/
├── src/
│   ├── app/                        # Top-level shell composition (App.tsx)
│   ├── components/layout/          # Header, sidebar, workspace primitives
│   ├── features/project/           # Project-facing UI (empty/welcome state)
│   ├── services/api/               # Reusable backend API client
│   ├── hooks/                      # UI behaviour hooks (useBackendHealth)
│   ├── core/project-model/         # Foundation domain model types
│   ├── styles/                     # Application shell styles
│   ├── index.css                   # Global reset/base styles
│   └── main.tsx                    # Frontend entry point
├── backend/
│   ├── app/
│   │   ├── __init__.py
│   │   ├── main.py                 # FastAPI app + CORS + router mounting
│   │   └── api/
│   │       ├── __init__.py
│   │       └── health.py           # GET /api/health
│   ├── conftest.py                 # Makes the app package importable in tests
│   ├── tests/
│   │   └── test_health.py          # Automated test for the health endpoint
│   └── requirements.txt
├── docs/
│   ├── architecture.md             # This file
│   └── project-model.md            # Future project model direction
├── .env.example                    # VITE_API_BASE_URL example for the frontend
├── package.json                    # Frontend build tooling (Vite, React, TS)
└── README.md
```

### Notes on structure decisions

- The frontend lives at the repository root (`src/`, `public/`, `package.json`,
  `vite.config.ts`) so both application parts share one repository without an
  extra wrapper directory. This matches the target layout in the Task A brief.
- `backend/app/` intentionally contains only `main.py` and `api/` right now.
  The `schemas/`, `core/`, and `services/` directories from the proposed
  layout are deliberately omitted: Task A has no request/response schemas
  beyond the health body, no shared core configuration, and no services to
  host. They will be introduced together with the features that need them,
  instead of shipping as empty placeholders.
- `forge-app/` is a leftover default Vite template generated by GitHub's
  mobile tooling and committed to the repository. It is not part of the Forge
  application and can be removed once the main app shell is verified.

## Frontend / backend boundary

### Frontend responsibilities

- Render the Forge UI and handle user interactions.
- Provide the shell for future graph editor, code editor, project management,
  and AI proposal workflows.
- Display backend connection status using the real health endpoint.
- Call the backend through a reusable API client
  (`src/services/api/client.ts`).
- Never contain provider API keys or other backend secrets.

### Backend responsibilities

- Provide HTTP API endpoints for Forge (currently only `GET /api/health`).
- In future phases: analyse Python source code, manage controlled project
  operations, integrate AI model providers, and validate proposed changes.
- Must not become a dumping ground for UI logic; keep endpoint ownership and
  business logic separation in mind when new features arrive.

### HTTP contract

- Base URL: `http://127.0.0.1:8000` (frontend configurable via
  `VITE_API_BASE_URL`).
- `GET /api/health` returns HTTP 200 with
  `{"status": "ok", "service": "forge-api"}`.

## Task A backend scope

Implemented now:

- FastAPI app entry with CORS restricted to the local Vite development origins
  (`http://127.0.0.1:5173`, `http://localhost:5173`).
- `GET /api/health` health endpoint.
- Automated test for the health endpoint using `pytest` and FastAPI
  `TestClient`.

Not implemented in Task A:

- Graph engine and graph editing endpoints.
- Code-editor integration endpoints.
- AI orchestration or provider calls.
- Source-code modification or validation workflows.
- Authentication, databases, Redis, or any deployment infrastructure.
